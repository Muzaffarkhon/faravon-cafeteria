# План миграции Neon → Supabase

**Дата составления:** 14 сентября 2026 г.
**Причина**: Neon Free исчерпывает 100 CU-hrs/месяц непредсказуемо (зависит от того, сколько сотрудников держат сайт открытым — SSE live-обновления опрашивают БД, пока открыта вкладка). Supabase Pro — $25/мес фиксированно, без почасового биллинга по compute — предсказуемее для бюджета при росте до 400+ сотрудников.
**Текущее состояние БД**: PostgreSQL на Neon, размер 37.92 МБ, 35 миграций Prisma, без специфичных Neon-расширений (postgis/pgvector и т.п. не используются) — миграция технически простая, риск в основном организационный (система уже в проде, сотрудники активны).

---

## 0. Принципиальное решение перед стартом

Мигрировать можно двумя путями:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Сейчас, под давлением лимита часов** | Решает проблему сразу | Риск ошибки выше — система уже используется живыми людьми, времени на тестирование мало |
| **B. Сначала апгрейд Neon (Launch, ~$10-15 до конца месяца), миграция — спокойно в течение недели** | Снимает срочность, миграцию можно сделать вечером/в выходной с полным тестированием | Придётся один раз заплатить Neon даже если потом уйдёте |

**Рекомендация: вариант B.** Апгрейд Neon снимает риск даунтайма прямо сейчас (уже обсуждали), а миграцию БД — операцию с реальными пользователями внутри — правильнее делать без спешки. Ниже план рассчитан на спокойный сценарий (можно сжать до 1 дня при необходимости, но с повышенным риском).

---

## 1. Подготовка (без риска для прод-системы)

1. **Создать проект Supabase** (supabase.com) — регион ближе к пользователям (AWS вариант в том же или соседнем регионе, что и текущий Neon `us-east-2`/Ohio, либо ближе к Таджикистану, если есть — трогать задержку сети).
2. **Сравнить лимиты плана**:
   - Free: 500 МБ БД, проект замораживается после 7 дней простоя (не проблема — сайт активен постоянно), но не годится для прод бессрочно.
   - **Pro ($25/мес)**: 8 ГБ БД включено, без почасового биллинга compute, backups 7 дней. Рекомендуется сразу на Pro, минуя Free — иначе рискуете тем же типом сюрприза, что и с Neon.
3. Получить строки подключения Supabase:
   - **Transaction pooler** (порт 6543, `?pgbouncer=true`) → аналог текущего `DATABASE_URL`.
   - **Direct connection** (порт 5432) → аналог текущего `DIRECT_URL`.
4. Локально (не трогая прод): поднять `npx prisma migrate deploy` на **пустой** тестовой Supabase-базе, прогнать все 35 миграций с нуля — проверить, что схема воспроизводится один в один без ручных SQL-костылей (в отличие от Neon, где часть миграций накатывалась вручную из-за отсутствия `DIRECT_URL`).
5. Прогнать `npx tsc --noEmit` и `npm run build` с `DATABASE_URL`, указывающим на тестовую Supabase-базу — убедиться, что рантайм-код (Prisma Client) не использует ничего Neon-специфичного.

## 2. Перенос данных (репетиция на тестовой ветке)

1. Снять дамп прод-данных из Neon:
   ```bash
   pg_dump "$NEON_DIRECT_URL" --no-owner --no-privileges -F c -f faravon_dump.bin
   ```
2. Восстановить в тестовую Supabase-базу:
   ```bash
   pg_restore --no-owner --no-privileges -d "$SUPABASE_DIRECT_URL" faravon_dump.bin
   ```
3. Сверить построчно ключевые таблицы (`Employee`, `User`, `Coupon`, `Application`) — количество строк должно совпасть 1:1 с Neon.
4. Запустить приложение локально с `DATABASE_URL`/`DIRECT_URL` на тестовую Supabase-базу, пройти ключевые сценарии: логин, выбор льготы, формирование купона, чат поддержки, админка — **на тестовых данных**, не трогая продакшен.

## 3. Переключение продакшена (само окно простоя)

Данные маленькие (38 МБ) — дамп/restore занимает секунды, основное время уйдёт на редеплой Vercel. Реалистичное окно простоя: **2–5 минут**.

1. Предупредить сотрудников заранее (например, объявление в Telegram-боте/на сайте за день), выбрать нерабочее время (ночь/раннее утро по Душанбе).
2. Снять **финальный** дамп с прод-Neon (уже без тестовых экспериментов, чистый прогон):
   ```bash
   pg_dump "$NEON_DIRECT_URL" --no-owner --no-privileges -F c -f faravon_final.bin
   ```
3. Восстановить в **боевой** Supabase-проект (уже созданный и провалидированный на шаге 1–2, но пустой от тестовых данных — либо создать отдельный чистый прод-инстанс Supabase, не путать с тестовым).
4. В Vercel → Project → Settings → Environment Variables (Production) заменить:
   - `DATABASE_URL` → Supabase transaction pooler
   - `DIRECT_URL` → Supabase direct connection
   - `SHADOW_DATABASE_URL` можно убрать из прод-окружения (нужен только для локальной разработки).
5. Редеплой (`git push` пустого коммита или Vercel → Redeploy).
6. Проверка сразу после деплоя: `/api/health`, логин под тестовым и реальным аккаунтом, страница купонов, чат поддержки, отправка тестового сообщения в Telegram-бот (боту тоже нужен доступ к той же БД).
7. Если что-то не так — **откат за 1 минуту**: вернуть старые `DATABASE_URL`/`DIRECT_URL` на Neon в Vercel, редеплой. Neon-проект не трогать/не удалять минимум 7 дней после переключения — это и есть план отката.

## 4. После переключения

- Neon-проект **не удалять сразу** — держать 7–14 дней как холодный резерв на случай, если всплывёт расхождение данных.
- Обновить `.env.example`, `docs/CRON-SETUP.md` (если меняются health-check URL), память проекта (`faravon-cafeteria-project.md` в auto-memory) — "прод БД теперь Supabase, не Neon".
- Проверить `scripts/*.ts` — все временные скрипты миграций/раннего периода ссылались на `DATABASE_URL`/`DIRECT_URL` из `.env`, менять не нужно, просто новые значения подхватятся автоматически.
- Пересчитать актуальность keep-warm/health-крона — Supabase Pro не спит (в отличие от Free), так что `/api/health`-пинги вообще не обязательны с точки зрения "не дать заснуть"; можно оставить редкий пинг только как мониторинг аптайма (UptimeRobot и так уже настроен для этого — можно возобновить с большим интервалом, например раз в 10–15 минут, для честного uptime-мониторинга, не как keep-warm).

## 5. Дальнейший риск-чеклист перед стартом (обязательно пройти)

- [ ] Есть подтверждённый бэкап Neon (дамп сохранён вне сервера, например локально/в облаке) — на случай если что-то пойдёт не так уже после переключения.
- [ ] Supabase Pro активирован и оплачен заранее (не в момент аврала).
- [ ] Тестовый прогон миграций и приложения на копии данных пройден без ошибок.
- [ ] Выбрано низконагруженное время для переключения.
- [ ] Есть человек (вы), готовый следить за системой минимум 30–60 минут после переключения.

## Итог

Миграция сама по себе не сложная технически (маленькая база, чистая схема, никаких Neon-специфичных фич) — но правильный порядок: **сначала снять срочность апгрейдом Neon, потом мигрировать спокойно с полной репетицией на копии данных**, а не наоборот. Готов начать с шага 1 (создание Supabase-проекта и тестовый прогон миграций), когда скажете.
