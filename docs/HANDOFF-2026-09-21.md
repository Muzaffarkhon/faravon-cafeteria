## 1. Касса подрядчика: скан без лишних тапов

Было: тап «Сканировать или ввести» → открывается камера → скан → ещё тап «Активировать». Плюс два пути к одному QR вели себя по-разному.

Стало (`src/app/(app)/provider/_confirm.tsx`):
- Камера видна сразу при открытии экрана кассы.
- Валидный купон гасится **сразу по скану** — и встроенной камерой кассы, и по ссылке из QR, открытой обычной камерой телефона (после входа). Общая функция `lookupAndRedeem`.

Защита не менялась:
- `/provider` без сессии → `/login?next=...` (возврат к тому же купону); роль без `coupons.confirm` → редирект.
- `lookupCoupon`/`redeemCoupon` на сервере заново проверяют сессию, право и принадлежность купона партнёру.

Исключение: **кешбек-купон** мгновенно не гасится — кассир вводит сумму покупки, поэтому такой купон ведёт в `CashbackForm` (сервер такой redeem и так отклоняет).

Ручной ввод номера и поиск по телефону не трогал — там подтверждение тапом осталось.

## 4. Авторегистрация в Telegram-боте по ФИО (PR #48)

Раньше: сотрудник делится контактом → номер не найден → бот открывает чат
поддержки и просит написать ФИО — дальше карточку вручную ищет и привязывает
C&B.

Теперь бот сначала пробует сам:
1. Гость пишет ФИО, должность и подразделение (в одном сообщении или в
   нескольких) — `resolveSelfRegistrationStep` (`src/lib/self-registration.ts`)
   ищет сотрудника нечётким совпадением по ФИО (`fuzzyNameKey`, тот же приём,
   что уже использует ручной поиск C&B), при нескольких похожих сужает по
   подразделению/должности.
2. Найден один кандидат → бот просит прислать номер телефона, который
   записан за ним в системе, **не называя сам номер**.
3. Точное совпадение → `verifyPhoneForCandidate` (`src/lib/telegram-link.ts`)
   сразу выдаёт логин и одноразовый пароль тем же путём, что и обычный вход
   по контакту (`issueForEmployee`), в аудите отмечено `via: "telegram:selfreg"`.
4. Три неверных номера подряд — кандидат сбрасывается, дальше обычный путь
   через администратора (можно попробовать заново с другим ФИО).
5. Кнопка «Написать администратору» теперь всегда вторая в клавиатуре бота
   рядом с «Поделиться контактом» — видна на каждом шаге.

Состояние — два новых поля на `SupportThread` (`regCandidateEmployeeId`,
`regPhoneAttempts`), без отдельной FSM-таблицы; миграция
`20260921130810_support_thread_self_registration`.

**Реализовано только в webhook-пути** (`src/app/api/telegram/route.ts` +
`src/lib/telegram-link.ts` + `src/lib/self-registration.ts`). Polling-бот
(`bot/bot.ts` + `bot/link.ts`, для локального запуска вне Next.js) не
дублировал — не используется ни в проде (там webhook через Vercel), ни в
песочнице. Если понадобится там — отдельная задача, код придётся продублировать
(так уже устроен весь остальной `bot/link.ts` — свой Prisma-клиент, не может
импортировать `server-only`-модули приложения).

Прогнано вживую в песочнице через прямые вызовы webhook-роута: полный цикл
(контакт не найден → ФИО → неверный номер → верный номер → логин и пароль) и
отдельно — исчерпание 3 попыток. Тестовые данные за собой убраны.

## 5. Pull-to-refresh перехватывал скролл во вложенных панелях (PR #49)

На страницах, где скроллится не вся страница, а панели фиксированной высоты
внутри (список диалогов + окно переписки в «Обращениях», и вероятно похожие
раскладки в других местах) — `window.scrollY` всегда 0, потому что сама
страница не скроллится. Встроенный `PullToRefresh` (`src/components/pull-to-refresh.tsx`)
проверял только `window.scrollY`, поэтому принимал обычный скролл внутри такой
панели за жест «потянуть, чтобы обновить» — скролл не работал, вместо него
запускалось обновление страницы.

Фикс: на `touchstart` (и повторно на `touchmove`) ищем ближайшего
прокручиваемого предка под пальцем; если он не в самом верху — жест его, а
не pull-to-refresh.

**Не проверено на реальном тач-устройстве** — эмулятор браузера не
воспроизводит нативный жест pull-to-refresh один в один, только код-ревью
механизма и смоук-тест в песочнице. Стоит перепроверить на телефоне.
