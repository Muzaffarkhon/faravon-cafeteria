## 1. Миграция БД: Neon → Supabase

Полноценный перенос продакшн-базы во время реальной эксплуатации (сайт уже был запущен, шли живые заходы сотрудников), с нулевой потерей данных.

**Как делали:**
1. Создан проект Supabase (Mumbai, `ap-south-1`), Data API/auto-expose/RLS отключены (не используются — вся работа через Prisma напрямую).
2. Схема развёрнута через `prisma migrate deploy` (все 34 миграции) — чистая история миграций, без дрейфа от Neon.
3. Данные перенесены `pg_dump --data-only` (Neon) → `pg_restore` (Supabase) через временный Docker-контейнер `postgres:18-alpine` (версия сервера Neon — Postgres 18, важно использовать совпадающую версию `pg_dump`/`pg_restore`).
4. **Построчная сверка** всех 27 таблиц Neon vs Supabase — полное совпадение. Отдельно найдены и исправлены 2 расхождения: сиды миграций (`RolePermission`, `SlaEscalationRule`) создали дефолтные строки, которые конфликтовали с реальными данными — приведены в точное соответствие вручную.
5. Финальная проверка перед переключением показала: активности с момента первого переноса не было (тихая ночь), повторной синхронизации не потребовалось.
6. Пользователь сам обновил `DATABASE_URL`/`DIRECT_URL` в Vercel (Settings → Environment Variables) и сделал redeploy — вариант A (без моего доступа к Vercel).
7. Проверено: новые записи (логины) после переключения пишутся уже в Supabase, Neon больше не растёт — переключение подтверждено.

**Важно:** пароль от БД Supabase прошёл через переписку в чате — **рекомендовано сменить** (Supabase → Settings → Database → Reset password) и обновить в Vercel, если ещё не сделано.

**Neon не удалён** — держим как бэкап на случай отката. Можно отключить через несколько дней/недель, когда будет уверенность, что всё стабильно (это также остановит расходы, если тариф Neon платный).

## 2. Производительность после переезда

**Проблема:** пользователь сообщил, что после переезда на Supabase выбор льготы стал отвечать заметно медленнее.

**Диагноз:** один клик «выбрать льготу» (`toggleSelection` в [`src/app/(app)/actions.ts`](file:///c:/Users/Acer/projects/faravon-cafeteria/src/app/(app)/actions.ts)) делает ~9–11 последовательных запросов к БД (сессия → RBAC → период → карточка → заявка → её позиции → транзакция создания в 4 шага → аудит-лог). Раньше Vercel (US) и Neon (US) были рядом — задержка round-trip маленькая. После переезда на Supabase (Mumbai) при Vercel-функциях по умолчанию в США — каждый round-trip получил ~200–250 мс трансконтинентальной задержки, то есть 2–3 секунды суммарно на клик.

**Фикс:**
1. [`vercel.json`](file:///c:/Users/Acer/projects/faravon-cafeteria/vercel.json) — `"regions": ["bom1"]`, функции Vercel теперь выполняются в Мумбаи рядом с Supabase (пользователь также подтвердил вручную в дашборде Vercel — заметно быстрее).
2. [`src/app/(app)/actions.ts`](file:///c:/Users/Acer/projects/faravon-cafeteria/src/app/(app)/actions.ts) — убран лишний round-trip: раньше всегда делался `upsert` (создать-или-вернуть заявку) + отдельный `findUnique` за позициями (2 запроса даже когда заявка уже существует). Теперь сперва пробуем получить заявку с позициями одним запросом; `upsert` вызывается только если её ещё нет.

**Замечание для следующей сессии:** регион Vercel `bom1` иногда недоступен на Hobby-тарифе — если после апгрейда/смены тарифа регион слетит, см. `vercel.json`.

### 3.3. Физика лепестков (`petal-drag.tsx`) — два бага
Пользователь заметил на десктопе: при перетаскивании одного лепестка соседние иногда двигаются без визуального касания, а иногда наоборот — не реагируют на явное касание, пока не отпустишь и не схватишь заново.

- **Баг 1 — устаревшие координаты.** Позиции нетронутых (просто дрейфующих по CSS-анимации) лепестков синхронизировались с реальным DOM только в момент начала перетаскивания (`onDown`). Пока идёт сам драг, их координаты «замораживались», хотя визуально они продолжают плыть — столкновения считались по неактуальной точке. **Фикс:** на каждом кадре физики, пока где-то идёт активный драг, координаты нетронутых тел пересчитываются из DOM (не нарушает принцип «0% CPU в покое» — работает только когда цикл физики и так уже крутится).
- **Баг 2 — раздутый невидимый радиус.** SVG-«листок» лепестка занимает в своём квадратном боксе только ~27% ширины (прозрачные поля по краям), а радиус столкновения считался как половина всего бокса — почти вдвое больше рисунка. **Фикс:** радиус пересчитан по геометрии самой формы (`petalRadius()` в файле) — зазор между невидимым и визуальным касанием сократился примерно втрое.

### 3.4. Проверка bfcache/logout (без изменений в коде)
Пользователь спросил про поведение кнопок «назад/вперёд» браузера после входа — оказалось нормальным поведением (сессия ещё активна). Дополнительно проверили более серьёзный сценарий — что происходит после **выхода** из аккаунта: убедились (на реальной prod-сборке `next start`, не в dev-режиме — там заголовок обманчиво усечён), что защищённые страницы отдаются с `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` — это дефолт Next.js для динамически рендерящихся страниц (все защищённые страницы читают cookies через `getSession()`, поэтому автоматически динамические). `no-store` исключает страницу из bfcache браузера — после logout кнопка «назад» не покажет замороженный снимок закрытой страницы. Изменений в коде не потребовалось (была пробная правка `proxy.ts`, но тест показал, что она ничего не меняла — откачена).
