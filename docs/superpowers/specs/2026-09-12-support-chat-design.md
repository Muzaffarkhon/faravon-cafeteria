# Чат поддержки: неопознанный человек в боте ↔ C&B в системе

**Дата:** 2026-09-12
**Статус:** утверждено в диалоге, готово к плану реализации.

## Зачем

Сейчас, если Telegram-бот не смог опознать человека (номер не совпал ни с
одним сотрудником, номер оказался у нескольких, код от HR неверный или
просрочен), бот отвечает текстом «обратитесь в HR» — и на этом всё. У
человека нет способа сразу спросить, что не так, а у C&B — узнать, что
кто-то застрял.

Цель: превратить этот тупик в переписку. Гость пишет прямо в бота, C&B
видит и отвечает из системы, ответ долетает обратно в тот же чат.

## Не делаем в этом заходе

- Привязку подрядчиков к боту по номеру (отдельная задача, отложена).
- Ответ C&B прямо из своего Telegram (только из системы — так виден общий
  статус «кто уже ответил» и не бывает двух ответов от разных админов
  вразнобой).
- Идентификацию личности гостя автоматически — сейчас это просто «кто-то
  из чата <telegramId>, возможно с номером телефона»; если в переписке
  выяснится, кто это, обычная привязка (по номеру/коду) остаётся отдельным
  процессом ботом же, не частью этой фичи.

## Данные

Две новые модели, не трогают `Feedback` (та остаётся про опознанных
сотрудников и своей лестницей статусов — модели разной природы, смешивать
не стоит).

```prisma
enum SupportThreadStatus {
  OPEN
  CLOSED
}

/// Один Telegram-чат — один тред, переоткрывается, а не плодится заново.
model SupportThread {
  id            String              @id @default(cuid())
  seq           Int                 @unique @default(autoincrement())
  telegramId    String              @unique
  /// Номер, который человек присылал (если делился контактом) — подсказка
  /// C&B, кто это, даже если официально не опознан.
  phone         String?
  status        SupportThreadStatus @default(OPEN)
  lastMessageAt DateTime            @updatedAt
  createdAt     DateTime            @default(now())

  messages SupportMessage[]

  @@index([status, lastMessageAt])
}

enum SupportMessageDirection {
  IN  // от гостя
  OUT // от C&B
}

model SupportMessage {
  id        String                   @id @default(cuid())
  thread    SupportThread            @relation(fields: [threadId], references: [id])
  threadId  String
  direction SupportMessageDirection
  body      String
  /// Кто из C&B ответил — только для OUT.
  authorId  String?
  author    User?                    @relation(fields: [authorId], references: [id])
  /// Прочитано C&B — только для IN, для счётчика непрочитанных.
  readAt    DateTime?
  createdAt DateTime                 @default(now())

  @@index([threadId, createdAt])
}
```

Миграция стандартная (`prisma migrate dev`), новые таблицы — риска для
существующих данных нет.

## Бот: где предлагаем кнопку

Единая точка — там, где `route.ts` уже ловит `SafeLinkError` и шлёт текст
ошибки. Если `e.message` содержит «обратитесь в HR» — а это все сообщения
о неудачной идентификации (номер не найден, номер у нескольких
сотрудников, код неверный/просрочен, учётка неактивна/отключена, Telegram
уже занят другим сотрудником) — добавляем `inline_keyboard` с одной
кнопкой «Написать администратору» (`callback_data: "support:start"`).
Правило намеренно общее (по подстроке, не по списку конкретных сообщений)
— новое сообщение об ошибке с той же фразой получит кнопку само, без
правки этого места.

Лимит попыток (`SafeLinkError` от `assertNotRateLimited`) кнопку **не**
получает — там правильный ответ «подождите», а не открывать ещё один канал
для перебора.

## Бот: обработка нажатия и дальнейших сообщений

Сейчас вебхук (`src/app/api/telegram/route.ts`) обрабатывает только
`update.message`. Добавляем `update.callback_query`:

- `data === "support:start"`: `answerCallbackQuery` (убрать часы на кнопке),
  создать или переоткрыть `SupportThread` для этого `telegramId` (если был
  `CLOSED` — вернуть в `OPEN`), отправить «Опишите вопрос — администратор
  увидит и ответит здесь же».

Дальше: любое обычное текстовое сообщение (не начинается с `/`) от
`telegramId`, у которого **есть** `SupportThread` (`OPEN` или `CLOSED` —
переоткрываем), сохраняется как `SupportMessage(direction: IN)` вместо
попадания в общий `WELCOME`. Команды (`/start`, `/code`, `/login` и т.д.)
продолжают работать как обычно даже при открытом треде — это осознанный
выбор: если человек внезапно вспомнил код от HR, он не должен быть заперт
в чате.

Уведомление C&B: если это первое `IN`-сообщение с момента открытия треда
или с последнего `OUT`-ответа (не дублируем на каждую строчку, если гость
пишет абзацами) — `notifyApprovers` с новым событием `SUPPORT_MESSAGE`,
тем же путём, что и уведомление о новой заявке (доставка через уже
существующий батч-механизм `notification-delivery.ts`).

## Приложение (webhook route.ts) вместо только бота

Логику callback_query и создания/переоткрытия треда кладём в
`src/lib/support-chat.ts` (аналог `telegram-link.ts`), вызывается из
`route.ts`. Локальный polling-бот (`bot/bot.ts`) в этом заходе не трогаем —
чат поддержки нужен только на проде (webhook); если понадобится и в
локальном боте — дублировать по той же схеме, что и `telegram-link.ts` →
`bot/link.ts`.

## Система: раздел «Чат поддержки»

Новое право `support.manage` (по умолчанию — `C_AND_B`, тот же общий
ящик без закрепления, как и решили).

- `/admin/support` — список тредов: гость «#<seq>», телефон если известен,
  превью последнего сообщения, бейдж непрочитанных, статус (открыт/закрыт),
  время. Сортировка — сначала с непрочитанным, затем по свежести.
- `/admin/support/[id]` — вся переписка (IN слева, OUT справа, как обычная
  лента чата), поле ответа + кнопка «Отправить» (server action:
  создаёт `SupportMessage(OUT)`, отправляет текст через уже существующий
  `sendTelegram` из `notification-delivery.ts`, помечает входящие
  прочитанными), кнопка «Закрыть диалог» (без подтверждения — не
  разрушительно, диалог просто переоткроется, если гость напишет снова).
- Пункт в меню (`_nav.ts`) рядом с «Обратной связью», со счётчиком
  непрочитанных тредов — тем же способом, что и текущий `pendingFeedback`
  в `layout.tsx`.

## Уведомление: шаблон

Новое событие `SUPPORT_MESSAGE` в `notification-format.ts`:

```
body: "💬 <b>Новое сообщение в чате поддержки</b>\n[[{phone}]]\nОткройте раздел «Чат поддержки»."
```

## Развёртывание

После выкладки — один раз перерегистрировать вебхук
(`npx tsx scripts/set-webhook.ts`) с `allowed_updates: ["message",
"callback_query"]` (правка в `scripts/set-webhook.ts`), иначе Telegram
не будет присылать нажатия кнопок вообще.

## Известные ограничения (осознанно, не блокеры)

- Гость может написать в чат сколько угодно раз без ограничения по объёму
  переписки — нет отдельного лимита на количество сообщений в треде
  (общий rate-limit `TelegramAuthAttempt` на это не действует, он про
  попытки идентификации). Если станет проблемой — добавить лимит на
  `SupportMessage.count` за окно, отдельной правкой.
- Один гость = один тред на всё время (по `telegramId`), история не
  чистится и не архивируется — это осознанно: если человек пишет полгода
  спустя снова, контекст полезен.
