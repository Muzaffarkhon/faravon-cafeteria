# Планировщик задач (cron)

`vercel.json` содержит 2 задачи с **суточным** расписанием (`0 2 * * *`,
`0 3 * * *`) — это единственное, что принимает бесплатный тариф Vercel Hobby
(любое расписание чаще раза в сутки ломает деплой). Суточный запуск для
уведомлений и SLA бесполезен — **реальную периодичность даёт внешний
планировщик** (cron-job.org и т.п., см. ниже). Суточный Vercel-крон оставлен
как минимальная подстраховка; на Pro-тарифе замени расписания на `*/10`/`*/15`.

| Путь | Нужная периодичность | Зачем |
|---|---|---|
| `/api/cron/deliver-notifications` | каждые 10 мин | добор недоставленных Telegram-уведомлений + оконные уведомления периода (§5.10) + автосмена периодов (§2): закрывает истёкший, открывает следующий по датам и создаёт черновик периода после него по шаблону (календарный месяц, окно выбора с 20-го числа) — ручное управление и правка дат в admin/periods остаются доступными |
| `/api/cron/sla-escalations` | каждые 15 мин | SLA-эскалации по зависшим заявкам (§5.12) |
| `/api/cron/daily-digest` | раз в сутки, начало рабочего дня | ежедневный отчёт по заявкам в Telegram для C&B и подрядчиков (§12). В `vercel.json` — `0 4 * * *` (UTC) = 09:00 Душанбе. Идемпотентно в рамках суток. |
| `/api/health` | **отключено с 14.09.2026** (было 2 источника пинга) | health-чек. Реальный виновник постоянной активности compute (~6 CU-hrs/сутки без остановки) — не этот cron-job.org крон (тот был раз в сутки), а **отдельный внешний UptimeRobot-монитор**, бивший `/api/health` каждые 5 минут непрерывно 13+ дней (см. dashboard.uptimerobot.com). UptimeRobot-монитор поставлен на паузу 14.09.2026. Cron-job.org задача "Фаровон — прогрев" тоже выключена (была не главной причиной, но раз уж искали — выключили заодно). Компромисс: первый запрос после простоя (autosuspend через 5 мин) может идти на 1–3 секунды дольше — приемлемо ради экономии Neon compute-часов. |

## Что нужно сделать

1. **`CRON_SECRET`** — задать в Vercel → Project → Settings → Environment Variables
   (Production). Vercel сам добавляет заголовок `Authorization: Bearer $CRON_SECRET`
   к cron-запросам, а роуты его проверяют. Без переменной cron-роуты отвечают 401.
   Сгенерировать: `node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"`.

2. **Тариф Vercel.**
   - **Pro / Enterprise** — расписания из `vercel.json` работают как указано (минутная гранулярность).
   - **Hobby** — cron ограничен: не чаще **1 раза в сутки** и **не более 2 задач**. Тогда:
     - оставить в `vercel.json` только 2 самые важные (`deliver-notifications`, `sla-escalations`),
       расписание Vercel всё равно сведёт к суточному;
     - **или** (рекомендуется для нормальной работы уведомлений) вынести планирование во
       внешний сервис — **cron-job.org** / GitHub Actions schedule / Upstash QStash:
       делать `GET https://<прод>/api/cron/deliver-notifications` и
       `.../api/cron/sla-escalations` каждые 10–15 мин с заголовком
       `Authorization: Bearer <CRON_SECRET>`, и `GET .../api/health` каждые 5 мин.

3. **Проверка после деплоя:**
   ```bash
   curl -H "Authorization: Bearer $CRON_SECRET" https://<прод>/api/cron/deliver-notifications
   curl -H "Authorization: Bearer $CRON_SECRET" https://<прод>/api/cron/sla-escalations
   curl https://<прод>/api/health
   ```
   Все три должны вернуть `{"ok":true,...}`.

Без работающего планировщика: оконные уведомления периода и SLA-эскалации не
отправляются, а недоставленные с первого раза Telegram-сообщения не добираются.
